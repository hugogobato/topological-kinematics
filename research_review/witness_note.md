# Phase 0 witness note (WP-0.2, gate G0)

**Status.** Operational correctness PASS. The Phase 0 witness suite executes 15 cases and all 15 pass (`research_review/results/phase0/witness/witness_results.json`). This note is a correctness artifact. It is not evidence of novelty, predictive value, data-extraction correctness, or application utility.

**Scope.** The suite tests the frozen finite-metric definitions of `research_review/assumption_ledger.yaml` and `research_review/metric_interface.md`: finite persistence diagrams, bottleneck distance with the L-infinity ground norm, strictly increasing timestamps, and the derived path diagnostics (interval speed, length, displacement, efficiency, speed-change rate, comparison angle, turn, triangle excess). Raw-data extraction belongs to gate G2 and is not tested here.


The runner writes `witness_results.json`, `witness_summary.txt`, `environment.json`, `run.log`, and four figures under `research_review/results/phase0/witness/`. It uses seed 20260920, takes about 7 seconds, and exits 0 only when every case passes. The frozen environment (Python 3.12.3, numpy 2.4.3, gudhi 3.12.0, persim 0.3.8, scipy 1.17.1, matplotlib 3.10.8, pytest 9.0.3, ripser absent) and the sha256 of every hashed input are recorded in `environment.json`; the tests run with pytest 9.0.3 from `pyproject.toml`.

**Numerical conditioning findings.** Three floating-point behaviors were discovered while building and verifying the suite, and all three are now explicit conventions rather than hidden ones. First, `gudhi.bottleneck_distance` can return denormal values (about `1e-308`) for a true-zero distance between non-identical diagrams, and identical diagrams can also return denormals; the public metric functions therefore apply the declared numerical-zero tolerance `1e-12` documented in the ledger and interface policy 13, and W-15 verifies the behavior. A consequence is that the public distance is a tolerance pseudometric at the `1e-12` scale: the exact triangle-inequality statements (R <= L, 0 <= eta <= 1) hold for the mathematical metric, and in the implementation a path with T intervals satisfies R - L <= T * 1e-12 and eta <= 1 + T * 1e-12 / L, so eta can exceed 1 inside the numerical band; the ledger and interface state these bounds, the numerical verification report exhibits the single-triangle deviation, and the final audit report exhibits the multi-interval deviation. Second, `arccos` is ill-conditioned near 0 and pi, and cancellation in `a^2 + b^2 - c^2` amplifies distance roundoff as steps approach zero; W-09 records this, the cosine-anomaly flag is surfaced instead of hidden, and structural angle checks use the exact brute-force reference while the library implementation is checked against it separately. Third, the raw library call is input-order sensitive on rare configurations (an overestimate of 1.4e-3 was found on one four-point pair); every public metric call canonicalizes its input, W-03 records a regression pair, and the public result matches the exact reference.

**Independent verification.** Three independent audits were performed and their findings were repaired and re-audited twice. The numerical verifier reimplemented the bottleneck distance, the formulas, and a 540-path falsification sweep from scratch (`research_review/results/phase0/verification/numerical_verification.md` with `independent_checks.py`); it found no violation on the declared input domain. The second-reader audit (`second_reader_audit.md`) recomputed every quantity on its own held-out trajectory using only the ledger and the interface, and found the numerical-zero ambiguity, the calibration-population gap, and several cosmetic documentation gaps. The consistency audit (`consistency_audit.md`) traced every numeric constant to the pilot specification and found one decision-rule non-equivalence. All blocking and material findings were repaired. The documented residuals are the inherited count ambiguity in the pilot specification's "six speed and speed-change summaries" wording, recorded in the pre-registration deviations log and deferred to the WP-1.2 feature-schema freeze, the cosmetic H3 discretion clause, and the tooling-only pyyaml omission in the pre-registration environment list. The numerical-zero rule, the calibration population, and the input canonicalization are explicit; the pre-registration GO rule matches the pilot specification exactly; and the interface defines the metric, the non-adjacent distance requirement, and the machine-readable output names. The three audit reports retain their original evidence and revision-2 hashes as historical records, and the fresh-eyes final audit in `research_review/results/phase0/verification/final_audit.md` recomputes hashes for the frozen revision. One propagation note: the plan's WP-2.2 verification target states `R <= L` and `0 <= eta <= 1` without the numerical-band qualification; the ledger and interface govern the implementation and carry the qualification.
